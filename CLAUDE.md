# Chezmoi Dotfiles

Personal dotfiles managed with [chezmoi](https://chezmoi.io) for cross-platform (macOS ARM64, Linux x86_64/ARM64) portability.

The chezmoi root is `home/` (see `.chezmoiroot`), so everything under it is relative to `~` on the target system.

## Templating

**Change detection (run_onchange scripts):**
```
# tmux-conf-hash: {{ include "dot_tmux.conf.tmpl" | sha256sum }}
```
Including a hash of a dependency in the script header causes chezmoi to re-run it when that file changes.

## Key Areas

- **Neovim config** — `home/dot_config/nvim/` — `home/dot_vimrc` is for real vim only; nvim never reads it. The `after/plugin/` tree is gone: every plugin's setup lives in its lazy.nvim spec and loads on a key, command or event, leaving catppuccin, lazy.nvim and nvim-treesitter as the only startup loads. Startup went from 56.6 ms to 24.9 ms, interleaved A/B on one machine with both caches warmed, 15 runs each. `.config/nvim/after` is in `home/.chezmoiremove`, since nvim sources anything under `after/plugin` whatever wrote it, so a leftover file would re-require what the specs now defer. Completion is Neovim 0.12's built-in, replacing `nvim-cmp`, `cmp-nvim-lsp` and `LuaSnip`. `vim.o.autocomplete = true` with `vim.lsp.completion.enable()` yields buffer words alone, because `'autocomplete'` draws from `'complete'`, whose default `.,w,b,u,t` names no language server protocol (LSP) source; the `o` flag added to `'complete'` routes through the `'omnifunc'` the LSP client installs. `autotrigger` stays off, since with `'autocomplete'` also on each keystroke fires two requests and the menu flickers to an unfiltered list between them. `conform.nvim` makes the `stylua` the flake already provides reachable from the editor. `lazy-lock.json` is managed by chezmoi, so a plugin update trips the "has changed since chezmoi last wrote it" prompt, the problem the VS Code `modify_` script exists to solve. `lsp/lua_ls.lua` guards `client.workspace_folders[1]`, which raised `ON_INIT_CALLBACK_ERROR` on every single-file Lua buffer.
- **Install scripts** — `scripts/` — see `scripts/CLAUDE.md` for the per-function breakdown. Versions are pinned: 25 `*_VERSION` constants in one block, resolved through `pinned_tag <pin> <repo>`, which returns the pin normally and the newest tag under `--upgrade`, and `make pins` prints every pin beside the current upstream tag. WezTerm is the one exception, carrying no pin: upstream has cut no tagged release since February 2024, so Linux downloads the rolling `nightly` tag, matching the `wezterm@nightly` cask macOS installs. Nothing had been pinned, so five machines could not be provisioned identically. `download_verified` checks SHA-256 where upstream publishes a manifest (ripgrep, sccache, cargo-nextest, atuin, cmake, nerd-fonts, wezterm, glow, treehouse, gitleaks, Go); where upstream publishes none, the comment says so. There is no `curl | sh` anywhere. Every vendor installer downloads to a temp file through `download()`, which sets `-f --proto '=https' --tlsv1.2`, and runs from disk. `make lint-sh` and `make fmt` cover the twelve scripts under `home/` (seven in `dot_local/bin`, the tmux status scripts, `wezterm-notify.sh`), which nothing had linted or formatted; they run under the posix dialect where the shebang is `#!/bin/sh`, with the style-only `SC2250`, `SC2249` and `SC2292` excluded and explained in the Makefile.
- **Nix and direnv** — the Nix installer appends a block to `/etc/zshrc` and `/etc/bashrc` that sources `/nix/var/nix/profiles/default/etc/profile.d/nix-daemon.sh`. `/etc/zshrc` is root-owned and a macOS update replaces it wholesale. On this Mac it is now byte-identical to the `/etc/zshrc.backup-before-nix` the installer left beside it, verified with `cmp`, so the block is gone, while `/etc/bashrc` still carries it in 8 occurrences of the string `Nix`. Only zsh lost the block. Nothing in the repo re-established it, `grep nix` over `home/dot_zshrc.tmpl`, `home/dot_zprofile.tmpl` and `home/dot_zshenv.tmpl` matching nothing, so neither `nix` nor `~/.nix-profile/bin` was on `PATH` at all. That directory holds exactly three entries: `bash` 5.3.15, `bashbug`, and `sh` symlinked to `bash`, which `install_modern_bash` in `scripts/install-common.sh` puts there on Darwin only, macOS shipping bash 3.2.57 as `/bin/bash`. With the profile directory off `PATH`, direnv resolved bash to 3.2.57 against nix-direnv's `use flake`, which requires 4.4 or newer, and every `.envrc` in a flake repository, this one included, failed with `direnv: nix-direnv: minimum required bash version is 4.4 (installed: 3.2.57(1)-release)`. The same regression stopped `./scripts/install.sh` dead after it printed "Xcode Command Line Tools already installed", with no error, no further output and exit status 0, under both the plain and the `--upgrade` form. The next step is `run_step install_nix`, which opens `if command -v nix || [[ -x /nix/var/nix/profiles/default/bin/nix ]]`; with nix off `PATH` the first test fails and the second passes, so it called `source_nix_profile`, a branch never taken before, because until the `/etc/zshrc` regression `command -v nix` always succeeded. `source_nix_profile` sourced `/etc/bashrc`, whose line 16 is `if [ -z "$PS1" ]; then`, and the installer runs `set -euo pipefail` under a non-interactive bash where `PS1` is unset. Reproduced directly, `bash -c 'set -euo pipefail; source /etc/bashrc'` prints "/etc/bashrc: line 16: PS1: unbound variable" and exits 1. It died inside `quiet`, which had redirected the step's stdout and stderr to a log file and runs the step in the current shell rather than a subshell, so the shell exited before reaching the reporting that names that log, hence a silent stop; replaying `run_step install_nix` against the pre-fix `install-common.sh` gives no output at all and exit 0. Three changes. `home/dot_zprofile.tmpl` gains a Nix block ahead of the Homebrew and elan blocks, sourcing the first readable of `nix-daemon.sh` (multi-user) and `~/.nix-profile/etc/profile.d/nix.sh` (single-user). It is not templated by operating system, both paths being guarded and the single-user one covering Linux. Placed first, so Homebrew keeps the front of `PATH` and the `~/.local/bin` entries in `.zshrc` keep the front of that. A real interactive login shell now puts `~/.nix-profile/bin` at position 9 and `/usr/bin` at 13, and `command -v bash` returns `~/.nix-profile/bin/bash`, 5.3.15. `nix-daemon.sh` exports `__ETC_PROFILE_NIX_SOURCED` and returns early on a second run, so a restored `/etc/zshrc` block is a no-op rather than a second `PATH` entry. Shadowing `/bin/sh` with the profile's `sh` costs nothing, `/bin/sh` on macOS being bash 3.2 in POSIX mode either way. Verified end to end: from a clean login shell, `direnv exec .` in this repo resolves make, shellcheck and stylua out of the nix store. Second, `source_nix_profile` no longer sources `/etc/bashrc`. It sources the profile scripts the block itself loads, `nix-daemon.sh`, then `/etc/profile.d/nix.sh`, then `~/.nix-profile/etc/profile.d/nix.sh`, which are written to be sourced from anywhere and reference nothing unguarded, and it unsets `__ETC_PROFILE_NIX_SOURCED` first, since reaching that function means `PATH` needs rebuilding whatever the variable says. Third, the `EXIT` handler now names the log file left behind by a step that took the shell down with it, and the run exits 1 instead of 0; `run_step` marks the failures it handled, so the new report covers only the ones it never saw, and the ordinary failing-step report and the clean path are unchanged, verified against all three. `scripts/verify-install.sh` gained the check that would have caught this, that a login shell resolves bash to 4.4 or newer. It probes with `env -i ... zsh -lc` rather than trusting the script's own doctored `PATH`, and clears the environment because inheriting `__ETC_PROFILE_NIX_SOURCED` would make the answer describe the caller instead of the machine. Separately, its tmux plugin check grepped the rendered `~/.tmux.conf` for the bare string `tmux-sensible`, which matched the comment above the four options inlined when that plugin was dropped, so it demanded a directory for a plugin the config no longer declares and reported FAIL on a correctly provisioned machine; it now reads every `set -g @plugin` line and checks each. `verify-install.sh` goes from 71 passed / 1 failed to 74 passed / 0 failed. The same check now ships to the target machine as `home/run_after_check-login-path.sh`, which chezmoi runs after every apply and which warns when a login shell resolves `bash` to anything older than the 4.4 that nix-direnv's `use flake` requires. It carries the same `env -i ... zsh -lc` probe as `check_bash_version`, duplicated deliberately, since `verify-install.sh` lives in the chezmoi source directory and a target machine is not required to have one, so the deployed copy has to work from `$HOME` alone. It runs after every apply rather than on a content hash, the change it watches for happening in `/etc`, where no hash of this tree can see it. It exits 0 either way, a non-zero status making `chezmoi apply` report an error no apply can fix, and it exits early when neither nix profile script is readable or when zsh is absent; the warning names the resolved bash and its version and points at `chezmoi apply ~/.zprofile`. It reads the profile scripts off disk rather than asking for `nix` on `PATH`, `PATH` being the thing under suspicion. Both paths were verified on this Mac, silent on a healthy machine and reporting `/bin/bash` at 3.2 when run against an empty `HOME`. The `Makefile`'s `DEPLOYED_BASH` now globs `home/run_*.sh`, so this script and the previously unlinted `home/run_onchange_install-claude-plugins.sh` are both covered by `make lint-sh` and `make fmt-ci`, and both pass; the glob stops short of the `.sh.tmpl` siblings, which neither tool can read until they are rendered.
- **Tmux** — `home/dot_tmux.conf.tmpl` — Hacktober theme, kept in sync with WezTerm's. `status-left` shows the armed `C-a` prefix as a ` ⌃a ` chip mirroring WezTerm's, driven by `#{?client_prefix,…}` rather than by polling, since tmux repaints the status line as soon as the prefix state changes. The chip is constant-width and signals by colour alone, so arming the prefix does not shift the window list. `status-right` forks once a tick: `cpu.sh`, `ram.sh` and `uptime.sh` are folded into one `.config/tmux/status.sh` emitting a single preformatted string, with the old targets listed in `home/.chezmoiremove`. It branches at runtime on `[ -r /proc/stat ]` rather than being a `.tmpl`, since that test is a shell builtin where a `uname` fork would not be, and the file stays a plain `.sh` inside the Makefile's lint glob. macOS support is ported from `wezterm.lua`, `ps -A -o %cpu=` with `sysctl hw.ncpu` and `vm_stat` with `hw.memsize`; before it, `cpu.sh` read `/proc/stat` and `ram.sh` read `/proc/meminfo` unconditionally, so both failed on macOS and `status-right` rendered empty fields. Linux CPU diffs `/proc/stat` across ticks through a state file, dropping a blocking `sleep 0.2` that was 218 ms of the old cost. Whole-tick cost at five windows, jobs started in parallel as tmux starts them, 25 runs: 335.9 ms ± 36.8 before, 148.4 ms ± 60.5 after. `status-interval` is 2, raised from 5. Interval 1 costs 287 ms of CPU a tick, near a third of a core held indefinitely on battery. `tmux-sensible` had never been installed on any machine — `install_tmux_plugins` cloned tpm and never ran `install_plugins`, so `~/.tmux/plugins/` held tpm alone and `history-limit` was still tmux's default 2000. Its options are inlined now (`history-limit 50000`, `aggressive-resize`, `display-time 4000`, `status-keys emacs`). tpm stays, since session persistence through resurrect and continuum genuinely needs a plugin, and its `run` line is guarded by `if-shell` so an unprovisioned machine still gets a working config. `base-index` and `pane-base-index` are 1 with `renumber-windows on`, because `#I` started at 0 while `wezterm.lua` renders `tab_index + 1`, putting `C-a 1` on the second window. `terminal-features` carries `hyperlinks` beside `RGB:extkeys`, verified present as `terminal-features[3]`; tmux's built-in `xterm*` feature set omits it, so OSC 8 links from delta, eza and gh were stripped inside tmux, defeating the ctrl-click handling in `wezterm.lua`.
- **claude-aware panes** — `~/.claude*/sessions/<pid>.json` records each live session's `cwd` and its agent identifier (`counter-fe`, the name `gwt` lists). Both terminals walk the pane's process subtree for a registered session and read the two off it, falling back to their old behaviour when there is none. The glob covers the work profile, since Claude Code keeps its whole state under `CLAUDE_CONFIG_DIR`, which the `cc-work` alias points at `~/.claude-work`, so that account registers its sessions in a directory of its own. Four readers looked only in the personal one, and a work pane therefore got no agent name, no cwd, no status bar and no bell. Every one of them now globs `~/.claude*/sessions`: `wezterm.lua` through `wezterm.glob`, once as the config loads, so a profile created afterwards arrives with the next reload; `home/dot_local/bin/executable_claude-pane-session` in its `have_sessions` guard and its cache build; `home/dot_local/bin/executable_claude-tab-title` in the ancestry walk that finds the calling session and in the stale-title prune; and `home/dot_claude/executable_wezterm-notify.sh` in the sessionId-to-pid lookup and the stale-bell prune. The title and bell directories stay single, at `~/.claude/tab-titles` and `~/.claude/tab-bells`, a pid being a machine-wide name that two profiles cannot both claim. The pruning in both scripts tests every profile now, so a run from one account no longer deletes the other's live entries. `sessions/` is deliberately not symlinked into `~/.claude-work/` the way `agents`, `commands`, `skills` and `output-styles` are, since it is mode 0700 and holds a per-session `.key` file beside each JSON. `claude-pane-session` lost its `ls -t` fork on the way. Ordering used to come from mtime within one directory, and a per-directory sort cannot order across profiles, so the lookup picks the most recently updated of the sessions it matches off the `statusUpdatedAt` it already parses. In `wezterm-notify.sh` the session-existence test is written inline rather than as a function, because shellcheck's SC2310 fires on a function called in a condition under `set -e`. Verified in a sandboxed `HOME`, a session registered only in the work profile resolves its name, its cwd and the amber busy bar where it previously returned the fallback, and with two live sessions in one pane's subtree, one per profile, the one with the newer `statusUpdatedAt` wins in both directions regardless of which file was written last. `claude-tab-title` run from a work session writes its title, and the prune keeps the other profile's live title while dropping a dead one. The live personal session still returns all four fields unchanged. `make lint-sh` and `make fmt-ci` pass, and the rendered `wezterm.lua` loads with no error.
  - *cwd* — new tabs/panes open where claude is *actually* working, not where the shell is. The two diverge once claude chdir()s (entering a worktree, say) while the shell sits suspended and never re-emits OSC 7.
  - *name* — tabs and windows are titled by agent, since `#{pane_current_command}` is `claude` for all of them alike. `wezterm-notify.sh` names its OS notification with it too, matching by `sessionId`.
  - *task* — `home/dot_local/bin/executable_claude-tab-title <word>` overrides that identifier with what claude is working on, keeping the two-character suffix (`chezmoi-d8` with task `atuin` renders `atuin:d8`) so several agents in one project still read apart. It writes a separate file under `~/.claude/tab-titles/`, since Claude Code rewrites the session JSON on every status change; `--clear` removes it, and overrides whose session has exited are pruned on the next write.
  - *status* — WezTerm tabs render as ` <index> ▎<title> `, the `▎` (U+258E) coloured amber `#e0a33e` while the session is busy, bold blue `#6f9ede` when `~/.claude/tab-bells/<pid>` marks attention (written by `wezterm-notify.sh`, removed once the tab is focused), blue when idle past 60 seconds, dim otherwise. Unfocused tabs only, since the active tab's state is already on screen in the pane below it. tmux windows draw the same chip: `window-status-format` and `window-status-current-format` in `home/dot_tmux.conf.tmpl` render ` <index> <bar><name> `, with the name truncated to 24 characters by `#{=24:...}`, the width WezTerm truncates a tab title to (`TAB_TITLE_MAX_WIDTH`). Before that they were ` <index>  <name> `, two spaces, no bar and no truncation. The index is painted at low contrast on both, `#6d371b` on the current or active chip (the midpoint of that chip's orange and the bar's black) and `#464444`, the tab bar's hover grey, elsewhere, mirroring `TAB_INDEX_FG_ACTIVE` and `TAB_INDEX_FG_INACTIVE` in `wezterm.lua`.
  - WezTerm does this in-process (`claude_session` in `wezterm.lua`). tmux shells out to `home/dot_local/bin/executable_claude-pane-session`, which the status line polls per window every tick — so `status-left` rebuilds a shared cache once per tick and the per-window lookups only read it. The bar's colour comes back from that script already wrapped in its own `#[fg=…]`, which works because tmux expands a `#()` job's output as a format, applying a style sequence inside that output rather than printing it; confirmed by attaching a client over a pseudo-terminal and decoding the SGR codes off the rendered status line. The script gained two fields for this, `status` and `status-current`, rather than one field and a flag, because tmux picks the chip by choosing between the two format options and the script cannot see which window is current. `status-current` always answers with the dim colour. A window with no claude session in it gets no bar at all, matching the WezTerm tab, so the empty string is the answer rather than a lookup miss. The shared cache carries two record kinds to serve this. The `S` session line holds `status` and `statusUpdatedAt` beside the name and cwd, and a new `B <pid>` line records a bell, whose existence is its whole content, so there is no file to read. Both window styles restore the name's own foreground and weight after the index and bar, since setting `#[fg=]` at all is what overrode `window-status-style`. Only the `status` fields fork `date` for the current time; `name` is asked once per window per tick and would be paying for nothing. The per-window freshness probe is `[ ! -f "$cache" ]`, replacing a `find -mmin` and keeping the safety net for a tick that finds no cache at all at zero fork cost. Process listing is `ps -eo pid=,ppid=`, the POSIX spelling; the old `ps -axo` mixed UNIX `-a` with BSD `x`, and the two return the same row count. The `/tmp` cache fallback carries `$(id -u)` in its name. Its comment claimed the path was per-user by construction, which was untrue: on a Linux SSH login without `pam_systemd`, `XDG_RUNTIME_DIR` is unset, and the sticky bit then makes `mv -f` fail against another user's file. `id -u` forks only in that fallback branch, never on the per-tick path.
- **Zsh** — `home/dot_zshrc.tmpl`. [fzf-tab](https://github.com/Aloxaf/fzf-tab) (cloned to `~/.local/share/fzf-tab` by `install_fzf_tab`) renders the completion menu as an fzf picker with per-context preview panes. Three things it depends on: `zstyle ':completion:*' menu no` (zsh's own menu would fire alongside it), `zstyle ':completion:*:descriptions' format` (its group headers come from that label), and being sourced after `~/.fzf.zsh` so it owns the `^I` binding. Make-target previews come from `_make_target_recipe`, which reads the recipe out of the makefile with awk — `make -n` would evaluate `$(shell ...)` on every keystroke. The picker is case-insensitive, which took an fzf flag rather than a completion setting. zsh's `matcher-list` already generated candidates case-insensitively: with it set, typing `Dow` produces `Downloads`, `dowager` and `downstream`, verified by driving an interactive zsh over a pseudo-terminal (pty) with fzf-tab disabled. fzf-tab then seeds fzf's query with the word already typed, and fzf is *smart-case*, so a query carrying an uppercase letter switches it to case-sensitive matching and the two lowercase candidates were filtered straight back out, leaving a picker that read as case-sensitive. `printf 'Downloads\ndowager\ndownstream\n' | fzf --filter=DOW` returns nothing; the same command with `-i` returns all three. So `-i` goes in the `zstyle ':fzf-tab:*' fzf-flags` line, at the cost of forcing a case-sensitive filter by typing a capital, which fzf has no per-keystroke toggle for. `${XDG_DATA_HOME:-$HOME/.local/share}/zsh/site-functions` is prepended to `fpath` before `compinit`, which reads `fpath` once. It holds the completion functions generated by `install_zsh_completions` in `scripts/install-common.sh`. Prepended rather than appended, so a generated function beats a system one claiming the same command name; before it there was no entry under `$HOME` on `fpath` at all, the five entries being system directories plus fzf-tab's lib. rustup ships `_cargo` and `_rustup` inside the toolchain, at `~/.rustup/toolchains/stable-<triple>/share/zsh/site-functions`, and puts them nowhere on `fpath`, so `cargo` and `rustup` completed nothing. That directory is added with a `stable-*` glob and the `(N)` qualifier, so a machine without rust does not hand compinit a path that does not exist. The glob matches more than one directory when a cross-compilation target is installed (this Mac has both `stable-aarch64-apple-darwin` and `stable-x86_64-unknown-linux-gnu`); the two carry the same functions, first match wins, and the extra costs compinit one directory scan a day. `delta --<TAB>` used to offer flags for Source Code Control System (SCCS). `_comps[delta]` read `_sccs`, because zsh's bundled `_sccs` registers the name `delta` for the SCCS subcommand of that name, and brew's `git-delta` ships no zsh function of its own. The fix is a real `_delta`, generated by `delta --generate-completion zsh` into the user directory; since that directory is first on `fpath`, compinit binds the name to it, and `delta --side<TAB>` now completes to `delta --side-by-side`. A guarded `compdef _delta delta` after compinit covers the case where the generated file is absent. Four further zstyles. `verbose yes` with `':completion:*:options' description 'yes'` puts each flag's description beside it, which the picker at 60% height has the width for. `special-dirs true` offers `.` and `..`, so `cd ..<TAB>` completes to `cd ../` where it previously completed nothing. `rehash true` makes completion notice a binary installed since the shell started, without a manual `rehash`. compinit's 24-hour freshness check no longer forks: it was `find "$ZDOTDIR/.zcompdump" -mmin -1440`, one fork on every shell startup, and is now zsh's own *glob qualifier*, `("${ZDOTDIR:-$HOME}"/.zcompdump(N.mh-24))` tested for emptiness. Measured in isolation the check went from 8.5 ms ± 0.8 to 6.1 ms ± 0.5, and whole-shell startup from 64.6 ms ± 2.1 to 58.0 ms ± 3.0. `install_zsh_completions` runs last in both platform scripts, since it invokes each binary to get its script. It covers `uv` (`generate-shell-completion zsh`), `uvx` (`--generate-shell-completion zsh`), `fd` (`--gen-completions zsh`), `delta` (`--generate-completion zsh`), `rustup` (`completions zsh`), `atuin` (`gen-completions --shell zsh`) and `chezmoi` (`completion zsh`). A tool whose completion is already installed system-wide is skipped rather than shadowed, so `brew upgrade` keeps ownership of it: on this Mac that skipped `atuin` and `chezmoi`, which brew links, and generated the other five. Homebrew links 38 completion functions on this Mac for comparison. On Linux none of the seven are skipped, which is the point, since `scripts/install-common.sh` drops those tools into `~/.local/bin` as bare binaries with no site-functions directory alongside, so Linux had completion for none of them. Output goes through a temporary file and is moved into place only when the generator exits clean and wrote something, so a generator that fails half way cannot leave a truncated function that breaks completion for that command until the next run. The step then deletes `.zcompdump` and `.zcompdump.zwc`, because compinit caches the command-to-function map in the dump and would otherwise wait out the 24-hour timer before seeing the new functions. A shell that finds the dump stale runs `compinit -C` on the old one and rebuilds in the background into `$dump.$$`, moved into place dump first and `.zwc` second; that 357 ms rebuild was the last large startup stall. `~/.zprofile` and `~/.zshenv` are managed as well. They hold `brew shellenv`, `~/.elan/bin` and `. ~/.cargo/env`, and going unmanaged was why a fresh Mac provisioned from the install scripts came up with no Homebrew on `PATH`. `LS_COLORS` is written out as a literal, since `dircolors -b` costs a 3.6 ms ± 0.9 fork per startup for a constant and the block runs before the PATH assignments, where a `command -v` would miss. Nothing on either platform set it, so the `list-colors` zstyle expanded an empty variable and the completion menu came out uncoloured; eza reads the same variable, so archives and images now render bold where they took eza's own defaults. `fzf-git.sh`, cloned by `install_fzf_git` and sourced after the fzf-tab block, binds `^G^B`, `^G^F`, `^G^H`, `^G^T` and `^G^R`. `GLOB_DOTS` is deliberately unset: it would make `*` match dotfiles, so `rm *` in a project directory would take `.git` with it.
- **Shell autosuggestions** — [zsh-autosuggestions](https://github.com/zsh-users/zsh-autosuggestions), cloned to `~/.local/share/zsh-autosuggestions` by `install_zsh_autosuggestions`, greys in the rest of the most recent matching command after the cursor. It is sourced last of the line-editor plugins, because it wraps every zsh line editor (ZLE) widget that exists when it loads and has to see fzf-tab's and atuin's. Ordering matters for a second reason: `atuin init zsh` sets `ZSH_AUTOSUGGEST_STRATEGY` to atuin's own `atuin` strategy, which draws the suggestion from the synced database rather than this machine's `$HISTFILE`, and that only holds if atuin runs first (a live shell reports `strategy: atuin`). Nothing in the config sets the strategy, so atuin's assignment stands. `ZSH_AUTOSUGGEST_HIGHLIGHT_STYLE` is `fg=#6c6c6c`, since the default colour 8 is invisible on the Hacktober background, and `ZSH_AUTOSUGGEST_BUFFER_MAX_SIZE=80` stops the widget rescanning history on every keystroke of a pasted or very long line. Loading it costs nothing measurable at startup: two rc files differing only in this block benchmark at 62.1 ms ± 2.7 against 61.5 ms ± 3.2 over 80 runs each, a 0.6 ms gap against a 3 ms run-to-run spread.
- **Shell history** — [atuin](https://atuin.sh) replaces syncing a shared `~/.zsh_history` between machines, installed by `install_atuin` in `scripts/install-common.sh` (`brew install atuin` on macOS, the official GitHub release tarball into `~/.local/bin` on Linux x86_64 and ARM64) and sourced in `home/dot_zshrc.tmpl` after the fzf-tab block. The config is managed too, at `home/dot_config/atuin/private_config.toml`; chezmoi's `private_` prefix lands it at `~/.config/atuin/config.toml` with mode 0600, matching the permissions atuin itself writes and leaving room for the `extra_headers` key, which can carry proxy credentials. `sync_address` points at a Tailscale host, `enter_accept = false` puts the selected command on the prompt rather than executing it, `update_check = false` because the install scripts own the version, and `[ui] columns` includes `host`, which the default set omits, so a synced result shows which machine ran it. Carrying the history file itself in a git repo does not work: it only ever appends locally, so two machines that both ran commands produce divergent tails that git sees as an unresolvable conflict. Marking it `encrypted_` (age or gpg) makes that worse, since the blob changes completely on every command, every sync becomes a full-file rewrite and no conflict can be resolved by hand. atuin syncs individual command records into SQLite instead, so machines merge. Encryption still matters on a private server, because shell history routinely carries API keys passed as command arguments and internal hostnames; atuin's sync is end-to-end encrypted with a key that stays on the machine, so the server only ever holds ciphertext. That key lives at `~/.local/share/atuin/key` and is deliberately not managed by chezmoi; losing it loses the synced history, so it needs backing up out of band in a password manager. Three keybinding details. `atuin init zsh` has to come after the `[ -f ~/.fzf.zsh ]` line, because `~/.fzf.zsh` binds `^R` to `fzf-history-widget` and the later binding wins. It is passed `--disable-up-arrow`, which would otherwise bind `^[[A` and displace the existing `up-line-or-beginning-search` bindings. And `--disable-ai`, since 18.19 binds `?` at an empty prompt to a TUI that sends the typed question to a hosted service — which defeats the point of keeping the history on a private server. `HISTFILE`, `HISTSIZE` and `SHARE_HISTORY` stay in place and atuin keeps writing the history file, which remains the offline fallback. The sync address is a Tailscale MagicDNS name and sits in the public repo deliberately, since the https certificate puts it in the public certificate transparency logs regardless and access is gated by the tailnet access control list (ACL) rather than by the name being unknown. `atuin register` / `atuin login` and the seeding step `atuin import auto` stay manual, and deploying the server itself is out of scope for this repo. A first sync or a bulk `atuin import auto` can leave a write-ahead log that every later process has to map and replay — 1.97 GB of `history.db-wal` after seeding 29,988 commands on 17 August 2026, which cost 520 ms before the `^R` TUI painted against 8 ms once `sqlite3 ~/.local/share/atuin/history.db 'PRAGMA wal_checkpoint(TRUNCATE);'` had folded it back into the database. Each machine records its commands under a short name rather than its hostname, so the Mac records `mac` where it used to record `Ben-MacBook.local`. The mechanism is `ATUIN_HOST_NAME`, which atuin reads when recording a command. (`ATUIN_HOST_USER` overrides the user half of the same string and is deliberately left unset.) The map lives in `home/.chezmoidata.yaml` under `atuin.hostnames`, keyed on `.chezmoi.hostname`, the hostname with any domain stripped and the case as the machine reports it. Current entries are `Ben-MacBook: mac`, `ben: manc`, `emel: emel`, `fisk: fisk`, `windows: win`, `av2: av2` and `av3: av3`. The key is what the machine reports as its hostname, which is not necessarily the name it is known by elsewhere: the Manchester box answers `ben` while its tailnet name is `ben-manchester`, and an entry written against the tailnet name matched nothing, so that machine silently kept atuin's default until the key was corrected. `home/dot_zshrc.tmpl` looks the machine up at `chezmoi apply` time and emits `export ATUIN_HOST_NAME=<name>` inside the existing `command -v atuin` block; a machine absent from the map emits nothing and keeps atuin's default, so the map does not have to be exhaustive. The `host` column is narrow, and a full hostname is truncated or crowds the command out of the row, which defeats the reason `host` is in `columns` at all — telling at a glance which machine a synced result came from. So the column is written `{ type = "host", width = 5 }` rather than the bare `"host"`, which takes atuin's default width of 15; the field is fixed rather than sized to its contents, and a database holding only `mac`, `manc`, `emel`, `fisk` and `win` still rendered every host field padded to 15 cells in atuin's search view, so the default spent 15 columns on `mac` as readily as on a full hostname and the 10 saved go to the command column, the one with `expand = true`. Every name in `atuin.hostnames` is four characters or fewer and the width includes the gap before the command column, so 5 is the tight fit, four of name and one of separator; at width 4 a four-character name butts directly against the command with no gap. A name wider than the field is truncated with `…` rather than overflowing (a name like `ben-manchester` at width 5 renders `ben-…`), so an over-long name costs only legibility, and padding is by display width rather than character count, so an emoji name (2 cells) pads correctly. Resolving the name at apply time rather than with a runtime `case` on `$(hostname)` leaves each machine's rendered `~/.zshrc` carrying only its own name, and keeps the map in one file instead of spread through shell branches. The caveat is that it applies only to commands recorded from that point on. Records already written keep the hostname, and `--filter-mode host` reads the old and new strings as separate machines; atuin has no rename command, and synced records are encrypted per record on the server, so back-filling is not available.
- **Git pager** — `core.pager` has to sit under `[core]` in `dot_gitconfig.tmpl`. It previously followed the `[diff "prose"]` header, where git read it as `diff.prose.pager` and ignored it, a diff driver taking `textconv`, `cachetextconv`, `binary`, `command`, `xfuncname` and `wordRegex` and no pager. `core.pager` was therefore unset and git fell back to `$PAGER`, so `git diff`, `git log -p` and `git show` rendered through bare moor and never reached delta, which is why `[delta] navigate` and `line-numbers` appeared to do nothing. `git add -p` was unaffected, `interactive.diffFilter` being a top-level key. Verified before the move by `git config --get core.pager` exiting 1 and `git var GIT_PAGER` returning moor.
- **Merge conflict style** — `merge.conflictStyle` is `zdiff3`, which needs git 2.35. An older git treats the unknown value as fatal, and not only on a merge. `git merge`, `git cherry-pick` and `git checkout -b` exit 128 with `unknown style 'zdiff3' given for 'merge.conflictstyle'`, and `git rebase` exits 1. Ubuntu 22.04 ships 2.34.1, so on that machine git could neither branch nor merge. `dot_gitconfig.tmpl` resolves the value at apply time: a template header runs `git --version` through `output`, takes the three-component number with `regexFind`, and `semverCompare ">=2.35.0"` chooses `zdiff3` or `diff3`. `lookPath` guards the call, so a machine with no git on `PATH` renders `diff3` and applies clean. Both styles show the common ancestor; zdiff3 also lifts lines common to both sides out of the conflicted region. `install_git` in `scripts/install-linux.sh` fits the git-core PPA on an Ubuntu machine below 2.35, so on a provisioned box the fallback is a safety net that never fires.
- **Prose diffs** — `home/dot_local/bin/executable_git-prose-split` splits a paragraph into one sentence per line, wired in as the `diff=prose` textconv driver in `dot_gitconfig.tmpl` and applied to `*.md`/`*.tex`/`*.txt` and friends by `home/dot_config/git/attributes` (`core.attributesFile`). Prose written a paragraph to a line makes a one-word edit read as the whole paragraph replaced; splitting it drops the untouched sentences out of the hunk, and delta's within-line highlighting picks out the changed words in the ones that remain. Display only — git turns textconv off for `add -p`, `format-patch` and anything else whose output must stay applicable, so the split diff never round-trips. No `cachetextconv`: that cache is keyed on the blob rather than on the script, so it would serve stale splits after every edit to the splitter. The abbreviation list (`e.g`, `Fig`, `et al.`, initials) is what stops `Fig. 3` breaking mid-sentence. A guard at the top of the script hands the file back through `cat` when `VSCODE_GIT_IPC_HANDLE` or `VSCODE_GIT_ASKPASS_NODE` is set. VS Code's git extension fetches the "original" side of its editor gutter diff with `git show --textconv` and compares it against the unsplit editor buffer, so a clean `.tex` file showed 144 split lines against 88 real ones and every paragraph read as several lines collapsing into one. `git status` never applies textconv, which is why the Source Control panel stayed empty while the gutter was full. The caveat is that VS Code exports both variables into its integrated terminal as well, so `git terminalAuthentication` can prompt through the UI; a `git diff` run there gets unsplit prose too, and setting `git.terminalAuthentication` to false is what would narrow the guard to the extension alone.
- **Box tables** — `home/dot_local/bin/executable_unbox` turns a rendered box-drawing table back into a markdown *pipe table*. Claude Code, `gh` and `glow` all draw a markdown table as box drawing, so a terminal selection copies the picture rather than the source, and pasting that into a `.md` file gives a preformatted block no renderer reads as a table. It takes files or stdin and passes non-table lines through untouched, so a whole pasted answer can go through it; `unbox -c` does the clipboard round trip, choosing between `pbpaste`, `wl-paste`, `xclip` and `xsel` by what is on `PATH` rather than by `WAYLAND_DISPLAY`. The separator and rule characters are matched as regex alternations of whole literal strings rather than as a bracket expression, because one-true-awk is byte-oriented and `[┌├└]` there is the set of six distinct bytes those three are built from; `0xE2` leads every box-drawing character and an em dash besides, so the bracket form would read a line of prose as a table rule. Whether two adjacent drawn rows are two table rows or one row wrapped over two lines cannot be read off the drawing, so it is decided per table by whether a rule ever sits between two body rows: Claude Code fences every row, so adjacent rows rejoin with the space the wrap replaced, while a table fenced only under its header gets one row per line. Alignment is not recoverable at all, centring being padding with spaces, so every column comes out left aligned. Counters are initialised in `BEGIN` rather than left to default, since an awk array subscript is a string and `a[n++]` with `n` unset writes the key `""` while `a[0]` then reads nothing back, which silently dropped the header row of any table not preceded by a non-table line. The `DEPLOYED_SH` glob already covers it, so `make lint-sh` and `make fmt` read it without change.
- **Claude Code settings** — `home/dot_claude/modify_private_settings.json.tmpl`, a one-liner including `.chezmoitemplates/claude-settings-modify.sh.tmpl`; the managed keys live in `.chezmoitemplates/claude-settings.json.tmpl`. Same `modify_` mechanism as the VS Code entry below, for the same reason. Claude Code rewrites the whole of `settings.json` whenever a setting changes and reorders every key while it does, so managing it as a plain file made each `/model`, `/output-style`, theme change or queued feedback draft trip chezmoi's "has changed since chezmoi last wrote it" prompt on a diff that was pure reordering. chezmoi owns the infrastructure keys, `permissions`, `hooks`, `statusLine`, `env`, `enabledPlugins`, `extraKnownMarketplaces`, `attribution`, `includeCoAuthoredBy` and `skipDangerousModePermissionPrompt`, and re-asserts them on every apply. `model`, `theme`, `outputStyle`, `effortLevel` and `feedbackDrafts` are left to Claude Code, so a `/model` on one machine stands. The first four of those are seeded from a second heredoc when stdin arrives empty, which is a machine with no `settings.json` yet; merging them on every run instead hoists their keys to the front of jq's output, so each reorder by Claude Code would be reordered back and the prompt this script exists to remove would return. chezmoi wants the type prefix ahead of the permission one, so the file is `modify_private_settings.json.tmpl`; spelled `private_modify_` it leaves the target unmanaged and reports nothing. There is no JSONC scrubber, unlike the VS Code script, since Claude Code writes strict JSON and a comment in that file would break Claude Code before it reached chezmoi.
- **Two Claude accounts** — a personal account and a work account, both signed in at once and switched from the shell. Claude Code ships no account switcher. `claude auth login`, `claude auth logout` and `claude auth status` exist, login taking `--claudeai` (the default), `--console`, `--email <addr>` and `--sso`, but a login replaces the credentials in whichever config directory is active, so one directory cannot hold two. The mechanism is `CLAUDE_CONFIG_DIR`, which relocates the whole config directory — credentials, `settings.json`, `.claude.json`, projects, history and sessions — and which the official documentation does not mention ([feature request](https://github.com/anthropics/claude-code/issues/33430)). Verified: `claude auth status` in the default directory reports the personal account on the max plan, while the same command under `CLAUDE_CONFIG_DIR` pointing elsewhere reports `loggedIn: false` with its own projects path, and writes a fresh `.claude.json` there while touching nothing in `~/.claude`. On Linux the credentials are a plain file, `~/.claude/.credentials.json` at mode 0600, so the split is clean. macOS puts them in the login keychain, and whether Claude Code namespaces the keychain item per config directory is unconfirmed; one shared entry would make the two profiles contend there, and it is untested on the Mac. `home/dot_zshrc.tmpl` gains `alias cc-work='CLAUDE_CONFIG_DIR=$HOME/.claude-work claude'` beside the existing `alias cc="claude"`, single-quoted so `$HOME` resolves when the alias runs rather than when `.zshrc` is sourced, which matters for a repo shared across five machines. A hyphen in a zsh alias name is fine, and alias expansion happens at the start of a command, so the `VAR=` prefix and any trailing arguments both pass through; verified by running `cc-work auth status` under an interactive zsh carrying only that alias. A second config directory starts empty of the whole customisation tree, so the work account would otherwise lose the agents, commands, skills and output styles, along with `CLAUDE.md`, `VOICE.md`, `PRACTICES.md` and `RTK.md`. `home/dot_claude-work/` therefore holds chezmoi `symlink_` entries pointing each of those back at `../.claude/<name>`, relative rather than absolute, so neither a `.tmpl` nor `{{ .chezmoi.homeDir }}` is needed and the links survive a home directory that moves. They are directory symlinks rather than per-file ones, deliberately: a link to the directory propagates additions and deletions as well as edits, so an agent written from a work session appears for the personal account, where per-file links would leave a *newly created* agent visible only to the profile that made it. Claude Code follows the link rather than skipping it, a made-up `zebrafish-audit` skill placed in a scratch directory and reached through a `.claude/skills` symlink coming back in a headless run's list of available skills. The sharing runs both ways, a file written through `~/.claude-work/agents/` appearing in `~/.claude/agents/`, and deleting it from the personal side removing it from the work side. Left unlinked as real per-profile files: `.credentials.json`, `.claude.json` (Claude Code writes it inside the config directory), `settings.json`, `projects/`, `history.jsonl` and `sessions/`, that separation being most of the point of a second profile. Both terminals glob every profile's session directory (the claude-aware panes bullet above), so `sessions/` staying per-profile costs the tab bar and the tmux status line nothing. The work profile's `settings.json` is its own `home/dot_claude-work/modify_private_settings.json.tmpl`, a one-liner including the same shared `.chezmoitemplates/claude-settings-modify.sh.tmpl` the personal profile uses, so both get identical `permissions`, `hooks`, `statusLine`, `env` and marketplace keys and the same seeded `model`, `theme`, `outputStyle` and `effortLevel` on a fresh machine, while each keeps its own per-session preferences; the script is config-directory agnostic and needed no change. The `Notification` hook command is written `~/.claude/wezterm-notify.sh`, an absolute path, so the work profile reaches the same script with no link of its own. `plugins/` is deliberately not shared, `enabledPlugins` living in the per-profile `settings.json` and `home/run_onchange_install-claude-plugins.sh` provisioning the default config directory alone, so the work profile needs its own `claude plugin install` run. That script is left as it is rather than extended, since `claude plugin marketplace add` against an unauthenticated config directory is untested.
- **VS Code** — `home/{Library/Application Support,dot_config}/Code/User/modify_settings.json.tmpl`, both one-liners including `.chezmoitemplates/vscode-settings-modify.sh.tmpl`; managed keys live in `.chezmoitemplates/vscode-settings.json.tmpl` (strict JSON, no trailing commas). It is a **`modify_` script, not a plain file**, because VS Code rewrites `settings.json` itself whenever a setting is toggled or a prompt is dismissed — managing it as a file made every such write trip chezmoi's "has changed since chezmoi last wrote it" prompt. The script receives the live file on stdin, strips JSONC comments/trailing commas, and `jq`-merges the managed keys over the top, so chezmoi owns a subset of keys and VS Code keeps the rest.
